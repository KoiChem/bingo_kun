# 効果音修正・検証記録

2026-10-30。対象は有機化合物ビンゴと元素記号ビンゴ。報告環境はiPadOS 17・Chrome。

初回だけの解除、resume未完了での使用可能判定、中断復帰の欠落を修正した。両アプリは同じ独立した `audio.js` を持ち、ユーザー操作内で同期的に再開要求を出す。runningを確認し、遅い短音は捨て、非表示・リセットで予約を停止し、終了ノードを切断する。元素ビンゴの確定2音は音声時計で0.1秒差に配置する。復帰できない場合にだけ「音声を再開」を表示する。

6件の状態制御テストで、再開の遅延・拒否・未完了、interrupted、closed、連打による要求重複、非表示・リセット後の古い音、時計による予約と切断、API例外を確認した。有機ビンゴの既存テストを含む15件が成功した。

ローカルChromiumで両アプリの初回モード切替・スタート・抽選を操作した。有機ビンゴでは実AudioContextのOscillator開始呼び出し15回と1/31への進行を観測し、メインと履歴の構造式画像読込を確認した。元素ビンゴではfaviconの既存404以外にエラーはなかった。

実機の可聴性は未確認。実iPadOS 17・Chrome、画面ロック・他アプリからの復帰、Bluetooth/外部出力と実スピーカーについては端末での確認が必要。模擬テストやHeadless Chromiumの発音要求を、音が実際に聞こえた証拠とは扱わない。OS消音・音量ゼロ・出力先はアプリで強制変更しない。

## 2026-10-30：シャッフル終了後に音が鳴る報告への修正

前回は`state === 'running'`だけを準備完了とし、実際に音声時計が進んでいるか検証していなかった。このため、runningだがcurrentTimeが止まっている場合に、全シャッフル音と確定音が同じ停止中の時刻へ予約され、時計が動き出してから鳴り得る欠陥があった。WebKitのiOS関連報告にもrunningと時計の進行が一致しない例がある。ただし、今回の実iPadでの直接原因がこれだったことは未確認。

修正前の回帰テストでは、停止した時計に12回のシャッフル音と1回の確定音、計13ノードが予約されることを確認した。そのテストは修正前に失敗した。

修正後は、ユーザー操作内でresume要求を出した後、音声時計が壁時計とともに進むことを確認してから発音を許可する。待機は最大700msで、準備できない間の音は予約しない。進行後に120msを超える時計のずれを検出した場合は発音を止め、既存ノードを停止・切断する。発音中は30ms間隔でも確認し、次の描画がなくても古い予約を残さない。停止が確認されたContextは次のユーザー操作でだけ作り直す。通常のBluetooth等の出力遅延だけを理由に永久にミュートする処理は追加しない。低遅延のlatencyHintを指定する。

音声回帰テスト10件、既存を含む19件が成功。ブラウザ上でも時計停止を模擬し、1/31まで抽選が進んでも音声ノード作成は0件、再開操作が表示されることを確認した。

実AudioContextを使ったローカルChromiumの時刻記録：

- 有機ビンゴ：最初のシャッフル発音予約は確定表示より1406.3ms前。確定音の予約は確定表示を更新したタスクと同時（観測差0ms）。発音の未来予約分は0ms。
- 元素ビンゴ：最初の発音予約は確定表示より2270.3ms前。確定2音の予約は確定表示更新と同時（観測差0ms）、2音目だけ意図どおり100ms後。
- 生の時刻記録は `audio-timing-orgo.json` と `audio-timing-element.json`。MutationObserverの壁時計、Oscillatorの予定時刻、currentTime、getOutputTimestamp、outputLatencyを記録した。

これは発音要求の回数だけでなく、表示の途中に音声時計が進みながら予約されることを確認した記録。スピーカーから実際に聞こえた時刻の測定ではない。物理的な音声出力先の遅延、および実iPadOS 17・Chromeでの体感同期は未確認。
